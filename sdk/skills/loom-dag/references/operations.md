# loom — как даг живёт на control plane

Этим справочником отвечают на вопросы «почему таск не стартовал», «где взять логи»,
«как поменять расписание», «что будет при перерегистрации».

---

## Путь от кода до рана

1. **Сборка образа.** Бинарник дага + `ENTRYPOINT` на него, образ пушится в registry.
2. **Регистрация проекта** — админка, раздел «Проекты». Регистрация **асинхронная**:
   запрос кладёт запись в очередь и сразу отдаёт `registration_id`, статус
   (`pending|running|success|failed`) админка поллит. Control plane запускает образ
   в режиме `describe` (docker-CLI или одноразовый k8s Job) и разбирает каталог.
3. **Шаблоны.** Каждый валидный даг каталога становится шаблоном проекта. Ошибка манифеста
   одного дага не отменяет регистрацию остальных; регистрация падает целиком, только если
   валидных дагов не осталось.
4. **Даги-инстансы.** От шаблона заводят сколько угодно дагов («завести даг»).
   Идентификатор — `проект/имя`.
5. **Ран.** Триггер вручную, по расписанию, backfill'ом или через API. На момент триггера
   пиннятся снапшот манифеста и digest образа — **ран переживает удаление дага и
   обновление образа**.
6. **Таск.** Планировщик раскручивает граф, кладёт таски в очередь, executor поднимает
   контейнер на попытку: 1 контейнер (k8s Job, `backoffLimit=0`) = 1 attempt.

## Обновление образа

- **auto_update** — control plane следит за digest тега проекта и перерегистрирует
  проект сам (в UI даг помечается «обновляется»).
- **«Обновить из registry сейчас»** — та же перерегистрация текущего образа по требованию.
  describe-Job всегда пуллит образ заново.
- Перерегистрация обновляет **шаблоны**, но не трогает настройки дагов-инстансов
  (расписание, пул, переменные, оверрайды ресурсов).
- Шаблон, пропавший из образа, не удаляется, а помечается `orphaned`: его инстансы
  работают на последнем известном манифесте, админка показывает предупреждение.

## Что настраивается в админке, а не в коде

| Настройка | Где |
|---|---|
| cron-расписание, `catchup` | карточка дага |
| пауза дага | карточка дага / список |
| пул слотов | карточка дага, таба «Настройки» (пул действует на все таски дага) |
| оверрайды ресурсов тасков | там же, приоритетнее значений из кода, по-полево |
| переменные и секреты | раздел «Переменные и секреты» или таба «Env» карточки дага |
| `run_ttl`, `run_keep_last`, `k8s_job_ttl` | глобальные настройки, уточняются на даге |

Смена пула применяется **со следующего рана** (пул денормализован в таск при триггере).

## Переменные и секреты: скоупы

Три скоупа, более узкий перекрывает более широкий при резолве на запуске таска:

```
глобальный ('', '')  ←  проектный (project, '')  ←  дага (project, dag)
```

Отсюда типовой приём для инстансов одного шаблона: общий `PG_DSN` — на проекте,
`SHOP` — у каждого дага свой.

Значения переменных видны всем аутентифицированным, значение секрета — по кнопке
(только admin или владелец дага). Скоуп существующей записи меняется одним действием,
значение при этом не вводят заново.

Что даг требует от окружения, видно в админке из манифеста: таба «Env» карточки дага
показывает состав и заполненность, незаполненные подсвечиваются бейджем в списке дагов
и строкой в «требует внимания» на обзоре.

## Ран и попытки

- **Статусы рана**: `running`, `success`, `failed`, `canceled`.
- **Ретрай попытки** — автоматический по `Retries` с удвоением паузы.
- **`RetryTask`** — ретрай таска и его подграфа из админки, **только на завершённом ране**
  (в том числе остановленном): успешные таски остаются успешными, доигрывается остаток.
- **Остановка рана** (`CancelRun`): ран и незавершённые таски получают `canceled`,
  живые попытки убиваются, лог коммитится, артефакты закрываются, ретрай не назначается.
- **Таймаут-watchdog** добивает попытку, зависшую дольше `Timeout` таска.
- **Зомби-reconcile** сверяет живые попытки с executor'ом после падения server'а.
- **Пик памяти попытки** семплируется executor'ом приблизительно: короткие спайки между
  семплами теряются, у коротких попыток значение может остаться пустым.

## Backfill и catchup

- `catchup` включает догон пропущенных тиков расписания, backfill — прогон за явный
  диапазон дат. И то и другое создаёт раны **пачками**.
- Ограничивай их `MaxActiveRuns` в коде дага, иначе пачка съест пул и вытеснит
  оперативные раны.
- Каждому рану пачки достаётся свой `logical_date` — таск обязан партиционироваться
  по нему (см. `pitfalls.md` §8).

## Логи и отладка

- SDK стримит строки лога на artifact-сервер с подтверждениями (без потерь и дублей,
  переживает рестарт сервера); дубль в stdout контейнера — страховка.
- Читаются логи через админку (карточка рана → таск), в том числе live с follow.
- Control plane дописывает в лог попытки строку об исходе (`attempt failed`, exit code,
  `OOMKilled`, `launch_failed`) — при смерти процесса это единственный след причины.
- В карточке рана есть снапшот фактической инъекции env (`run_env`): какие переменные
  и секреты, из какого скоупа реально уехали в контейнер. Первое место, куда смотреть
  при «а почему он взял не тот DSN».

Порядок разбора упавшего таска:

1. exit_reason попытки — `Error` / `OOMKilled` / `launch_failed` / `canceled`;
2. лог попытки (последние строки + строка об исходе от control plane);
3. `run_env` — что реально было в окружении;
4. воспроизведение локально: `go run . run --params='...'` с теми же переменными
   в окружении процесса.

## Retention

Ран удаляется, если нарушает **любой** из лимитов: `run_ttl` (старше срока) или
`run_keep_last` (за пределами N последних завершённых дага); `0` отключает критерий.
Порядок удаления: артефакты → логи → запись в БД. Раны удалённых дагов чистятся
по глобальным лимитам.

## Внутрикластерные соединения

SDK ↔ artifact-сервер и SDK ↔ control plane не аутентифицируются (токенов нет —
осознанное решение), но все каналы переживают обрыв: писатель артефактов досылает
неподтверждённый хвост, follow-читатель переоткрывается со своего offset'а, лог-синк
дедуплицирует по seq. Рестарт artifact-сервера или control plane **не роняет** живые
таски.
