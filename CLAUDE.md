# loom

Оркестратор пайплайнов (аналог Apache Airflow) с дагами на Go: docker-образ
(«проект») несёт один или несколько дагов, от каждого дага образа
(«шаблона») заводят сколько угодно дагов-инстансов со своими настройками;
таски запускаются экземплярами того же образа, данные между тасками текут
персистентными стримами через artifact-сервер.

## Модули (go.work)

- `sdk/` — публичная либа для дагов (пакет `loom`): `loom.Main(dags...)` —
  в одном бинарнике может быть несколько дагов, `describe` печатает
  **каталог образа** (`{sdk_version, dags:[{name, manifest|error}]}`), нужный
  даг выбирается `run --dag=<name>` или env `LOOM_DAG`; внутри `sdk/streamstore/` —
  общая стейт-машина файловых стримов (единственная реализация, используют и
  artifact-сервер, и локальный режим). Все gRPC-подключения SDK — через общие
  dial-опции (`grpc_dial.go`): keepalive для быстрого обнаружения мёртвого
  соединения, агрессивный reconnect-backoff, ретрай unary на UNAVAILABLE
- `api/` — proto-контракты (`api/proto/`) и сгенерированный код (коммитится)
- `artifact/` — data plane: артефакты **и логи тасков** (отдельные
  streamstore-каталоги: `DATA_DIR` и `LOG_DIR` — у лог-стримов свой
  жизненный цикл), каркас по gotemplate
- `server/` — control plane, **stateless** (без дискового состояния):
  Postgres (mobone) + gRPC/gateway, **асинхронная** регистрация проектов
  (очередь `project_registration`, claim `FOR UPDATE SKIP LOCKED`; сам
  `describe` — docker-CLI, а при `EXECUTOR=k8s` — одноразовый k8s Job,
  `k8sdescriber`), планировщик (очередь `FOR UPDATE SKIP LOCKED`, чистый
  planner + executor-порт, cron-триггер по `next_run_at` с catchup-режимом,
  ретраи `up_for_retry` с backoff, таймаут-watchdog, зомби-reconcile),
  executor'ы k8s и docker (`EXECUTOR=k8s|docker|none`), retention
  (лимиты — настройки в БД, см. ниже), ретрай таска/подграфа (`RetryTask`,
  только на завершённом ране), принудительная остановка рана (`CancelRun`),
  параметры рана и `logical_date`, backfill, значения тасков (XCom,
  `run_value`), пулы слотов с приоритетами (пул можно закрепить за дагом,
  см. ниже) и `max_active_runs`, переменные
  и секреты с env-инъекцией (`SECRET_KEY`), пользователи с ролями,
  агрегаты дашборда. Логи не хранит — финализирует (`FinishTaskLog`) и
  проксирует чтение (`ReadTaskLog`) с artifact-сервера
- `examples/` — примеры дагов
- `admin/` — админка: Nuxt 4 SPA (`ssr: false`) + Nuxt UI v4 (НЕ Naive UI;
  образец — проект caravaneer). Раздел «Проекты» (регистрация образа,
  каталог его дагов, «завести даг» от шаблона, sync, авто-обновление,
  размер образа и SDK; страница шаблона
  `/projects/<проект>/templates/<шаблон>` — граф, таски и требования к
  окружению, общие для всех его инстансов), дашборд (карточки плиткой;
  секция «требует внимания» — только когда есть что показать; окно графика
  активности подстраивается под возраст данных: сутки по часам у молодой
  инсталляции, иначе дни, потолок — 2 недели),
  карточка дага (`/dags/<проект>/<даг>`;
  схема до первого запуска), метрики ранов, читабельные логи, переменные
  и секреты одним разделом `/env` (тип — колонка и фильтр), пользователи,
  глобальные
  настройки инсталляции (`/settings`, admin-only в наве); из действий —
  «обновить даг из registry сейчас» и «остановить ран» (в списке ранов и в
  карточке рана); в карточке дага — таба «Настройки»: пул дага, уточнения
  настроек («Хранение и лимиты») и редактор оверрайдов ресурсов тасков, и
  таба «Env»: что даг требует от окружения (переменные и секреты из
  манифеста с описаниями из кода дага, статус «не заполнена» и заполнение
  глобально/локально на месте); незаполненные видны бейджем в списке дагов
  и строкой в «требует внимания» на обзоре.
  Страница рана — граф вместо таблицы тасков: в узле статус, номер попытки,
  длительность, пик памяти и кнопка ретрая. Переходы между
  страницами анимированы (`app.pageTransition` + классы `.page-*`).
  Цветовая тема (акцент + затонированный под него фон) выбирается в подвале
  сайдбара: `classic` (дефолт — прежний вид) и `naive` (палитра тёмной темы
  Naive UI: почти чёрный фон, мятный акцент, малый радиус)
  — палитры в `main.css` (`:root[data-loom-theme=…]`), выбор в localStorage,
  семантика статусов от темы не зависит. Раздаётся server'ом на
  `ADMIN_PORT` (8081)
  из `ADMIN_DIR` (`make build-admin`), рантайм-конфиг — `/config.js` из env
  `ADMIN_API_BASE_URL`; дев — `pnpm dev` + `.env` (+ `HTTP_CORS=true` на
  gateway). После правок: `pnpm typecheck` → `pnpm lint`. См. `admin/README.md`

## Ключевая семантика (кратко)

- **Проект = образ, шаблон = даг в образе, даг = инстанс шаблона.** Один
  бинарник объявляет несколько дагов (`loom.Main(a, b)`), `describe` отдаёт
  каталог; server сохраняет проект (`project`: образ, digest, auto_update) и
  его шаблоны (`dag_template`: манифест, `orphaned`), а от шаблона заводят
  даги-инстансы (`dag`, RPC `CreateDag`). Идентификатор дага **составной** —
  `(project, name)`, во всех путях API и админки; в SQL — пара колонок
  `project_name`/`dag_name`, в Go — `dagModel.Ref` (встроен в `Main`,
  поэтому `d.Name`/`d.Project` работают как раньше).
- **Инстансы одного шаблона различаются настройками, а не кодом**: у каждого
  свои расписание, пул, оверрайды ресурсов и — главное — свои переменные и
  секреты (даг на магазин: `SHOP=mechta` и `SHOP=technodom`). Конфига
  инстанса в API нет: параметризация идёт через env-значения.
- Шаблон, пропавший из образа, **не удаляется**, а помечается `orphaned`:
  его инстансы продолжают работать на последнем известном манифесте, а
  админка показывает предупреждение. Ошибка манифеста одного дага не
  отменяет регистрацию остальных (итог по дагам — в записи регистрации);
  регистрация падает, только если валидных дагов не осталось совсем.
- Таск запускается тем же образом, `LOOM_DAG` = имя шаблона (снапшот
  `run.template`) — ран переживает удаление дага.

- Артефакт скоупится на попытку `(run_id, task, attempt, name)`;
  `writing → committed | aborted`; follow-читатели с tail-follow.
- Commit выходов — по успеху таска (`return nil`), abort — по ошибке/панике.
  `Close()` выхода опционален и НЕ коммитит. Commit подтверждается
  artifact-сервером: успешный return таска гарантирует данные на диске.
- `After` — ждать успеха отправителя; `AfterStreamed` — ко-старт и чтение по
  мере записи (opt-in).
- Локальный режим: `<dag-binary> run [--params='{...}']`, артефакты и
  значения в `.loom/runs/<run-id>/`, остаются после рана.
- Мелкие значения тасков — `rt.PushValue`/`rt.PullValue` (через control
  plane, лимит 64KB); параметры рана — `rt.Params()`/`rt.BindParams()`,
  «дата данных» — `rt.LogicalDate()`.
- Распределённый режим: `run --task=<name>` + env-контракт `LOOM_*`;
  программный вход — `DAG.RunTask`. Внутрикластерные RPC (SDK ↔ servers) не
  аутентифицируются (токенов нет — осознанное решение).
- **Расписание задаётся в админке, не в коде дага**: `schedule`/`catchup` —
  колонки `dag` (RPC `SetDagSchedule`), в манифесте `describe` их нет.
  В SDK остался только `MaxActiveRuns` (свойство реализации пайплайна).
  Пул слотов — там же, в админке (см. ниже).
- **Регистрация проекта асинхронная**: `RegisterProject` кладёт запись в
  очередь и сразу отдаёт `registration_id`; статусы
  (`pending|running|success|failed`) и итог по дагам образа админка поллит
  через `ListProjectRegistration`. Авто-обновление по digest (dagsync)
  сверяет тег **на проект** (один запрос в registry вместо запроса на каждый
  даг) и ставит в ту же очередь с `source=auto` — отсюда индикация
  «проект обновляется» в UI. `SyncProject` (кнопка «обновить из registry
  сейчас») кладёт в ту же очередь перерегистрацию **текущего образа**
  проекта с `source=manual` — обновление по требованию, без ожидания тика
  `DAG_SYNC_TICK`; describe-Job в k8s всегда пуллит образ
  (`imagePullPolicy: Always`), иначе sync пиннил бы старый слой с узла.
  Заодно с регистрацией по registry API резолвится **размер образа**
  (`project.image_size_bytes`: config + слои, сжатыми — сколько тянет pull;
  единый источник для обоих executor'ов). Best effort: недоступный registry
  регистрацию не валит, прежнее значение сохраняется.
- **Остановка рана** (`CancelRun`, права как у триггера — владелец дага):
  ран и его незавершённые таски получают терминальный `canceled`, живые
  попытки убиваются через executor и финализируются обычным путём (attempt —
  `failed` с `exit_reason=canceled`, лог коммитится, артефакты закрываются,
  ретрай не назначается). Успешные таски остаются success, поэтому
  остановленный ран доигрывается `RetryTask` (принимает и `canceled`-таск).
  Гонку claim→launch закрывает проверка статуса рана в `launch`:
  забранный таск остановленного рана не запускается, а сразу закрывается.
- **Пул задаётся только на даге, не в коде** (колонка `dag.pool`, RPC
  `SetDagPool`, поле `pool` в `RegisterDag`; права — владелец дага): пул
  действует на все таски дага, пусто — общий `default`. В SDK и манифесте
  пула нет (опция `loom.Pool` удалена, поле `DagTaskMain.pool` —
  `reserved`). Резолв при триггере рана: пул денормализован в
  `task_instance`, поэтому смена применяется со следующего рана.
  Существование пула проверяется заранее (`PoolCheckerI`) — даг с
  неизвестным пулом навсегда завис бы в очереди.
- **Права на проект и на даг**: `user_project` открывает все даги проекта
  (включая заведённые позже), `user_dag` — точечно; проверка —
  `authz.RequireProject`/`RequireDag`.
- **Auth**: пользователи в Postgres (`app_user`, bcrypt), сессии — opaque-
  токен, в БД только его sha256 (`session`); первый админ создаётся через
  саму админку, пока пользователей нет (`CreateFirstAdmin`, race-safe через
  `LOCK TABLE`). Роли: `admin` — всё; `user` — читает всё, меняет только
  назначенные ему даги (`user_dag`): расписание/пауза, их переменные и
  секреты, триггер/ретрай/backfill. Роль метода проверяет интерцептор
  (`server/internal/app/auth.go`), права на конкретный даг — usecase через
  `internal/authz`. `ADMIN_TOKEN` больше нет.
- **Настройки инсталляции — в БД, не в env** (таблица `setting`, RPC
  `SettingService`, страница `/settings`): `run_ttl`, `run_keep_last`,
  `k8s_job_ttl` (можно уточнять на даге — скоуп как у переменных, локальное
  перекрывает глобальное), `dag_reg_ttl` (только глобальная). Env
  `RUN_TTL`/`K8S_JOB_TTL`/`DAG_REG_TTL` упразднены; реестр имён и
  валидация — `server/internal/domain/setting/model.Defs`, фоновые процессы
  перечитывают значения на каждом проходе (правки без рестарта).
- **Retention — по времени И по количеству**: ран удаляется, если нарушает
  любой из лимитов (`run_ttl` — старше срока, `run_keep_last` — за
  пределами N последних завершённых дага; 0 отключает критерий). Проход
  идёт по дагам (включая удалённые из `dag` — их раны чистятся по
  глобальным лимитам); порядок прежний: артефакты → логи → запись БД.
  `k8s_job_ttl` резолвится планировщиком при launch и уезжает в Job как
  `ttlSecondsAfterFinished` (0 — Job'ы не удалять); слишком маленькое
  значение сужает окно зомби-reconcile после падения server'а.
- **Оверрайды ресурсов тасков из админки** (таблица `task_resources`, RPC
  `List/Set/DeleteTaskResources`, права — владелец дага): значения
  `loom.Resources` из кода дага — рекомендуемые, непустое поле оверрайда
  приоритетнее; мердж по-полево в `launch`, поэтому подхватывается
  ретраями без перерегистрации. Все поля пустые — оверрайд снимается.
- **Переменные и секреты** — три скоупа: глобальный (`('', '')`),
  проектный (`(project, '')`) и дага (`(project, dag)`); более узкий
  перекрывает более широкий при резолве в `launch` (общий тип
  `commonModel.Scope`, цепочка — `Scope.Chain()`). Скоуп настроек
  (`setting`) — такой же. Значения переменных видны всем
  аутентифицированным, значение секрета — по кнопке (`GetSecretValue`,
  только admin/владелец дага). Скоуп существующей записи меняется одним
  RPC (`MoveVariable`/`MoveSecret` — UPDATE адреса, права нужны на оба
  скоупа): значение переезжает как есть, поэтому секрет не приходится
  вводить заново, а занятое имя в целевом скоупе — ошибка, а не тихая
  перезапись. Смена типа (переменная ↔ секрет) — другая сущность, её
  админка делает парой set+delete, и значение секрета там вводят заново.
  В SDK: `Secret(env, name[, description])` и
  `Variable(env, name[, description])` (env-пространство общее — дубли
  ловит валидация манифеста). Необязательное описание уезжает в манифест
  (`describe`) и показывается в админке при заполнении значения.
- **Что даг требует от окружения — видно в админке**: состав переменных и
  секретов берётся из манифеста (он их несёт с самого начала), а
  заполненность резолвится по тому же правилу, что при `launch` (локальное
  перекрывает глобальное). Отдельного RPC нет — резолв клиентский
  (`admin/app/utils/dagenv.ts`, как и `runenv.ts` для снапшота рана):
  карточка дага (таба «Env»), бейдж в списке дагов и блок «требует
  внимания» на обзоре считают его из `GetDag`/`ListDag` + `ListVariable` +
  `ListSecret`. Заполнить можно прямо из табы — глобально или локально.
- **Метрики попыток**: пиковое потребление памяти семплирует executor
  (docker — `docker stats --no-stream`; k8s — metrics.k8s.io, тик
  `K8S_METRICS_TICK`, 0 — выключено) и шлёт событием `metrics` в тот же
  канал, что started/finished; планировщик пишет `attempt.peak_memory_bytes`
  (`greatest` — идемпотентно). Значение приблизительное: короткие спайки
  между семплами теряются, у коротких попыток может остаться null.
- Логи тасков: SDK → artifact-сервер (`artifact_v1.TaskLogService`,
  bidi-стрим с seq/ack) — **без потерь и дублей**, обрыв переживается
  реконнектом с досылкой неподтверждённого хвоста; дубль каждой строки в
  честный stdout (fd 1/2 перехватываются dup2) — только страховка на случай
  смерти процесса, основной канал — стрим. Commit лог-стрима делает
  планировщик (`FinishTaskLog`, дописывает исход попытки).
- Реконнекты — во всех соединениях; рестарт artifact/server не роняет таски:
  - лог-синк: буфер неподтверждённых строк, seq-дедупликация на сервере;
  - писатель артефактов: bidi с байтовыми ack'ами и resume — обрыв стрима
    без commit/abort НЕ абортит запись (streamstore: `Release`/`ResumeWrite`,
    судьбу брошенного стрима решает `FinishAttempt`);
  - follow-читатель артефактов: переоткрытие со своего offset'а;
  - unary (values, finish, stat): gRPC retry policy;
  - полный буфер (32k строк лога / 4MiB записи) блокирует таск
    (backpressure) — данные не дропаются, пока попытка жива;
  - чтение лога админкой: `after_seq` в `server_v1.ReadTaskLog` — обрыв
    follow-стрима переживается докачкой без потерь и дублей.
  - **предел ожидания зависит от режима** (`artifactcli.reconnectLoop`):
    follow-чтение реконнектится без предела (обязано пережить рестарт
    artifact-сервера), а разовое (лог без follow, скачивание артефакта)
    сдаётся через `readReconnectBudget` и отдаёт 503 — иначе админка
    бесконечно висит на пустой панели вместо ошибки. Прогресс (отданные
    строки/байты) начинает серию заново, поэтому долгое чтение с редкими
    обрывами в бюджет не упирается.

## Деплой

Helm-чарты живут в отдельной репе — в этой их нет и на них не оглядываемся.
Dev-стенд — `deploy/dev-stand/`: инфраструктура (Postgres, registry) в
kubernetes docker-desktop, процессы loom нативно (`go run`, `pnpm dev`),
таски — docker-контейнерами. Порты и доступы зафиксированы в его README,
менять их не нужно. Контекст kubectl указывать явно
(`--context docker-desktop`), дефолтный может смотреть на боевой кластер.
CI (`.github/workflows/ci.yml`) пересобирает и пушит образ только при
изменении content-хэша его входов (git-блобы модуля + общие `api/`/`sdk/`,
для server ещё `admin/`): digest тега `latest` без изменений не меняется, и
деплой, следящий за digest'ом, не рестартит нетронутые поды.

## Проверка

```bash
make test    # + в сомнительных случаях: go test -race ./... по модулям
make build
cd examples && go run ./demo-etl run
cd examples && go run ./multi-dag describe          # каталог образа с двумя дагами
cd examples && go run ./multi-dag run --dag=orders_etl
```

Интеграционные тесты `server/test` требуют Postgres: `TEST_PG_DSN=postgres://...`
(без него — skip). Берём базу `loom_test` в Postgres dev-стенда
(`deploy/dev-stand/`), отдельный контейнер поднимать не нужно:

```bash
TEST_PG_DSN='postgres://postgres:postgres@127.0.0.1:30432/loom_test?sslmode=disable' make test
```

Если БД всё же поднимается контейнером — **только через docker** (не через
Postgres.app/initdb) и **без `--rm`**: контейнер с `--rm` умирает на
`docker stop` вместе с данными, а их регулярно хочется посмотреть после
