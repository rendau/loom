# 00 — Product Discovery

Дата: 2026-08-25. Источник: код `admin/`, proto-контракты `api/proto/server_v1`,
CLAUDE.md, вводные владельца продукта.

## Что за продукт

Админка **loom** — оркестратора пайплайнов (аналог Airflow), где один
docker-образ = один даг на Go. Админка — операционный инструмент: через неё
следят за выполнением, разбирают провалы, управляют дагами, расписаниями,
переменными/секретами, пулами и пользователями.

Nuxt 4 SPA (`ssr: false`) + Nuxt UI v4, раздаётся control plane server'ом
на `ADMIN_PORT`, рантайм-конфиг — `/config.js`. API — grpc-gateway (REST).

## Пользователи

| Тип | Права | Сколько |
|---|---|---|
| Админ | всё: даги, env, пулы, пользователи | 1–3 |
| Пользователь | читает всё; **меняет только назначенные ему даги** (`user_dag`): расписание/пауза, env дага, триггер/ретрай/backfill/остановка | 3–7 |

Масштаб данных: **27 дагов** в бою, логов немного, ранов — сотни в
день максимум. Это малые данные: плотность и скорость диагностики важнее
масштабируемых списков.

**Ключевое ограничение среды: маленький экран ноутбука** (рабочий вьюпорт
~1180px). Горизонтальный скролл — главный раздражитель сегодня.

## Чем реально занимаются в админке (по частоте)

1. **Разбор упавшего рана**: какой таск упал, почему (лог, exit reason),
   с какими параметрами/переменными выполнялся, ретрай.
2. **Слежение за идущими ранами**: что сейчас выполняется, как долго,
   live-лог.
3. **Изучение логов** (упавших и живых попыток).
4. **Мониторинг ресурсов дага**: потребление памяти, время выполнения,
   «жирные» таски (где память/время).
5. **Работа с артефактами**: просмотреть/скачать данные, созданные между
   тасками, для личного анализа. — *сегодня в UI недоступно вообще*
6. **Потребление volume artifact-сервера**. — *сегодня недоступно*
7. Реже: регистрация/обновление дагов, env, backfill, пулы, пользователи.

## Доменные объекты и связи

```
Даг (name, image, schedule, paused, manifest: таски)
 ├── Регистрация (очередь: pending|running|success|failed, source auto|manual)
 ├── Ран (execution: running|success|failed|canceled; trigger, logical_date, params,
 │        снапшот манифеста)
 │    ├── Таск-инстанс (pending|queued|starting|running|up_for_retry|success|
 │    │                 failed|upstream_failed|canceled; attempt N)
 │    │    └── Попытка (starting|running|success|failed; exit_code/reason,
 │    │         peak_memory_bytes)
 │    │         ├── Лог (стрим с artifact-сервера, follow, after_seq)
 │    │         └── Артефакты (run_id, task, attempt, name) — data plane
 │    └── Значения (XCom: task, key, value ≤64KB)
 ├── Переменные/Секреты дага (скоуп dag_name; глобальный скоуп '' перекрывается)
 └── Назначения пользователям (user_dag)

Пул (name, slots) ← таски всех дагов конкурируют за слоты
Пользователь (admin|user + dag_names)
```

Таск манифеста объявляет привязки env: `Variable(env, name)` /
`Secret(env, name)` — видно в манифесте, какие имена каких
переменных/секретов таск получает.

## Существующие паттерны

- Навигация: `UDashboardSidebar` (collapsible), плоский список разделов.
- Все списки — `UTable`; действия — ряды icon-only ghost-кнопок с UTooltip.
- Модалки подтверждений с текстом последствий (хорошие).
- `useApiAction` — единый loading + тосты успеха/ошибки.
- Поллинг: разный на каждой странице (30с дашборд, 3с ран/регистрации,
  нет на списке ранов).
- Статусы: `utils/status.ts` — единые цвета/подписи (badge).
- Лог-вьювер — сильный компонент (виртуализация, парсинг, follow, reconnect).
- Граф дага — свой SVG, слоистая раскладка, статусы цветом, клик → лог.
- `CopyText` для длинных строк (образ, digest, run id).
- View Transitions между страницами.

## API-поверхность (server_v1, gateway)

Dag: Register/List/Get/SetSchedule/SetPaused/Sync/SetAutoUpdate/Delete +
ListDagRegistration/Get. Run: Trigger/List/Get/RetryTask/Cancel/Backfill.
TaskValue: List. TaskLog: Read (stream, after_seq). Variable/Secret:
List/Set/Delete (+GetSecretValue). Pool: List/Set. User: CRUD. Auth:
Status/FirstAdmin/Login/Logout/Me. Dashboard: Get.

`RunGetRep` включает `manifest_tasks` — снапшот манифеста рана (граф,
привязки env).

### Чего в API нет (важно для redesign)

1. **Артефактов**: ни списка артефактов рана/таска, ни чтения/скачивания
   через gateway. `artifact_v1` — внутренний data plane без auth, наружу
   не выставлен.
2. **Потребления volume** artifact-сервера.
3. **Значений переменных на момент рана**: привязки (env → имя) есть в
   `manifest_tasks`, но резолв (какое значение реально ушло в под) нигде
   не фиксируется — переменную могли поменять после запуска.
4. **Агрегатов по дагу**: длительность/память по таскам за историю ранов
   («жирные таски») — только пер-ран attempts.
5. **Последних статусов ранов в ListDag** (для мини-истории в списке дагов).

## Технические ограничения (не ломать)

- Nuxt UI v4 — основа; свои компоненты — только поверх.
- Рантайм-конфиг `/config.js`, раздача server'ом, `ADMIN_PORT`.
- Роли admin/user + `user_dag` (`canManageDag`).
- Бэкенд вне scope: новые методы — только как требования в
  `07-implementation-plan.md`.
- Anti-goal: «современный дашборд» с крупными пустыми метриками и
  градиентами. Плотность и скорость диагностики важнее эффектности.

## Открытые вопросы

1. Артефакты бывают большими (стримы между тасками) — какие лимиты
   превью в браузере разумны? (предложение: превью первых N КБ + скачивание
   целиком)
2. «Значения переменных рана»: достаточно ли снапшота на момент launch
   (требование к API), или хватит текущих значений с пометкой «могли
   измениться»? (предложение: снапшот — единственно честный вариант)
3. Пулы — оставить отдельной страницей или свернуть в раздел
   «Администрирование»? (предложение: оставить страницу, сгруппировать
   в сайдбаре)
