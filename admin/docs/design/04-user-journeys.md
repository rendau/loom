# 04 — User Journeys

Ключевые сценарии в новой IA. Формат: цель → вход → шаги → информация →
провалы/восстановление → выход. «Владелец» = admin или user с назначенным
дагом.

---

## J1. Разбор упавшего рана (главный сценарий)

**Цель:** понять, что и почему упало, устранить, доиграть ран.

**Вход:** Обзор («требует внимания»), либо `/runs?status=failed`, либо
ссылка от коллеги `/runs/<id>?task=<t>`.

**Шаги:**
1. Обзор: провал показан как «даг · таск · когда · exit reason» → клик.
2. Открывается ран с **уже выбранным упавшим таском**: лог последней
   попытки виден без дополнительных кликов, отфильтрованные error-строки
   заметны, граф показывает место таска в пайплайне.
3. Оператор смотрит лог (поиск/фильтр уровня), при необходимости:
   - таба «Env» — с какими значениями переменных запускался;
   - контекст рана — params, дата данных;
   - таба «Артефакты» — заглянуть во входные/выходные данные;
   - таба «Попытки» — если ретраи были, чем кончались (exit code/reason,
     память — не OOM ли: пик рядом с memory_limit из манифеста).
4. Решение: (а) починить env → таба Env → переход в `/env` на нужную
   запись → исправить → назад; (б) виноват код — идти чинить образ.
5. «Ретрай таска» из инспектора → подтверждение с описанием сбрасываемого
   подграфа → ран снова running, инспектор в follow-режиме лога.

**Информация:** статус+exit reason, лог, env-значения, params, память
попытки vs limit, артефакты, граф.

**Провалы:** лог пуст (под умер до строк) → инспектор показывает
exit_reason и подсказку «см. попытку N / source=srv»; артефакт aborted →
статус стрима виден. Ретрай недоступен (ран running) → кнопка не
показывается, причина — в пустом состоянии.

**Выход:** ран success; Обзор больше не показывает этот провал.

## J2. Слежение за идущими ранами

**Цель:** убедиться, что текущие раны идут нормально и не зависли.

**Вход:** Обзор, блок «Выполняется сейчас» (авто-поллинг).

**Шаги:** блок показывает даг, сколько идёт, и «дольше обычного» если
длительность превысила типичную → клик → ран: граф живой, текущий таск
running, клик → лог follow. Список `/runs` тоже авто-обновляется.

**Провалы:** ран завис → «дольше обычного» подсвечен; владелец может
остановить ран из шапки (подтверждение с последствиями).

**Выход:** раны завершились; при провале — J1.

## J3. Мониторинг дага (память / длительность / жирные таски)

**Цель:** понять поведение дага во времени и найти тяжёлые таски.

**Вход:** `/dags/<name>` (таба «Обзор»).

**Шаги:**
1. Список последних ранов со статусами, длительностями, Σ памяти.
2. Блок «Таски по ресурсам»: топ по средней длительности и пиковой памяти
   (агрегат за последние N ранов — API-требование; fallback — последний
   завершённый ран), рядом лимиты из манифеста → видно и «жирных», и
   «близких к OOM».
3. Тренд длительности ранов (мини-бар по последним ранам, как activity).
4. Углубиться: клик по рану → J1-экран; клик по таску → инспектор в
  контексте выбранного рана.

**Выход:** решение — поднять лимиты (в коде дага), перепланировать
расписание, или «всё в норме».

## J4. Просмотр/скачивание артефакта

**Цель:** забрать данные между тасками для локального анализа.

**Вход:** ран → инспектор таска → таба «Артефакты».

**Шаги:** список артефактов попытки (имя, размер, статус стрима) →
«Скачать» (файл через gateway) или «Превью» (первые ~64КБ текстом, с
пометкой обрезки). Для writing-артефакта — размер растёт, скачивание
доступно по текущему хвосту (streamstore умеет follow) либо честно disabled —
решается в имплементации API.

**Провалы:** артефакт aborted → показан статус и попытка; нет прав — нет
таба нет (артефакты читают все аутентифицированные, как логи).

**Выход:** файл на диске оператора.

## J5. Поиск конкретного рана

**Цель:** найти вчерашний backfill-ран дага X за дату D.

**Вход:** `/runs`.

**Шаги:** селект дага (27 значений, с поиском) → чип «backfill» → в
таблице видна «Дата данных» → строка → ран. URL со всеми фильтрами можно
переслать коллеге.

## J6. Изменение конфигурации (env дага)

**Цель:** поменять переменную/секрет дага, не сломав запуски.

**Вход:** `/env?dag_name=<x>` (из карточки дага или инспектора таска).

**Шаги:** как сегодня (страница удачная): фильтр уже установлен → правка
значения → сохранение. Подтверждение удаления предупреждает про
launch_failed. Новое: из инспектора таска переход ведёт сразу на запись.

## J7. Регистрация / обновление дага (admin)

**Цель:** добавить даг или выкатить новую версию образа.

**Вход:** `/dags` → «Зарегистрировать»; обновление — «⋯ → Обновить из
registry» на строке/карточке.

**Шаги:** как сегодня (асинхронная очередь, статусы поллятся). Изменения
только подачи: активные регистрации — компактная строка статуса, провал
регистрации — заметный alert с ошибкой describe (единственное место, где
её видно — сохраняется). Бейдж «обновляется» на даге остаётся.

**Провалы:** describe упал → alert на `/dags` и в карточке (история
регистраций на табе «Схема»).

## J8. Первый вход нового оператора

**Цель:** составить картину системы без обучения.

**Шаги:** `/login` → Обзор: видно, что выполняется, что упало, что
запланировано → имена дагов ведут на карточки с графом → термины UI
совпадают с SDK (даг, таск, ран, попытка, пул, переменная, секрет).
Пустые состояния объясняют (уже частично есть: «зарегистрируйте
docker-образ», подсказки loom.Variable/Secret — сохранить).
