# loom — подводные камни при написании дагов

Список конкретных мест, где даг ломается тихо или неочевидно: §1–27 — сам SDK,
§28–33 — работа с внешними системами (источниками и приёмниками любого рода).
Проверяй по нему чужой даг и свои правки.

---

## 1. Побочные эффекты в `main()` и конструкторах дага

Тот же бинарник запускается:

- в режиме `describe` — контейнером при **каждой** регистрации/синке проекта;
- в режиме `run --task` — на **каждую попытку каждого** таска.

В обоих случаях исполняется весь `main()` и конструкторы всех дагов образа. Значит:

```go
// ❌ регистрация проекта упадёт, и каждый таск тоже
func main() {
	db := mustConnectPG(os.Getenv("PG_DSN"))   // при describe env пустой
	loom.Main(newDag(db))
}

// ✅ соединение внутри таска
dag.Task("load", func(ctx context.Context, rt *loom.Runtime) error {
	db, err := pgxpool.New(ctx, os.Getenv("PG_DSN"))
	...
}, loom.Variable("PG_DSN", "pg_dsn", "DSN основной БД"))
```

Сюда же: `log.Fatal` на незаполненную переменную, чтение файлов конфига, `init()`
с сетевыми вызовами, тяжёлые вычисления при построении графа (`describe` ждут).

## 2. `bufio.Scanner` и строки длиннее 64KB

Дефолтный `Scanner` отдаёт `bufio.ErrTooLong` на строке >64KB. Артефакт со строками
JSON на запись легко его превышает — и таск падает только на проде, на реальных данных.

```go
sc := bufio.NewScanner(in)
sc.Buffer(make([]byte, 0, 64*1024), 16*1024*1024) // либо bufio.Reader.ReadString('\n')
```

## 3. Забытый `Flush` буферизованного писателя = обрезанный артефакт

Самая дорогая из тихих ошибок. Писать в `rt.Output` без буфера медленно, поэтому
поверх него кладут `bufio.Writer` / `json.Encoder`. Если перед выходом из таска не
позвать `Flush()`, хвост данных останется в буфере, таск вернёт `nil`, **и loom
закоммитит обрезанный артефакт как валидный**. Получатель примет его за полные
данные и, если это сверка, удалит «лишнее» из приёмника.

```go
w := jsonl.NewWriter(out)      // bufio.Writer внутри
...
if err := g.Wait(); err != nil {
	return err
}
return w.Flush()               // ← обязателен, и именно в успешной ветке
```

`defer w.Flush()` не годится: его ошибка потеряется, а таск вернёт успех.

## 4. Конкурентная запись в один выход

`rt.Output` отдаёт один поток на весь таск. Несколько воркеров, пишущих в него
одновременно, перемешают строки (а `bufio.Writer` вообще не потокобезопасен).
Оборачивай писателя своим мьютексом — см. `patterns.md`, «Параллельность внутри таска».

## 5. Проглоченная ошибка = закоммиченные битые данные

Commit выходов делает Runtime по `return nil`. Если ошибка записи или разбора не поднялась
наверх, ты закоммитил половину артефакта, и получатель примет её за полные данные.

```go
// ❌
for _, v := range items {
	fmt.Fprintln(out, v)          // ошибка записи потеряна
}
return nil

// ✅
for _, v := range items {
	if _, err := fmt.Fprintln(out, v); err != nil {
		return err
	}
}
```

То же с `defer`: `defer out.Close()` ничего не коммитит и не «спасает» — Close лишь
запрещает дальнейшую запись.

## 6. Чтение транзитивной зависимости

`rt.Input`/`rt.PullValue` доступны только для **прямых** рёбер. `load` после `transform`
не может читать артефакты `extract`, даже если `transform` зависит от `extract`.
Нужны данные — объяви ребро явно (`loom.After(extract), loom.After(transform)`).

## 7. Опциональный выход, который никто не создал

Если отправитель по ветке кода не вызвал `rt.Output("x")`, читатель `x` **блокируется**
до завершения попытки отправителя и получает `NOT_FOUND`. Это не зависание, но и не
пустой файл. Либо всегда открывай выход (пусть пустым), либо передавай признак
значением (`PushValue("has_x", false)`).

## 8. Стримовый читатель падает вместе с отправителем

`AfterStreamed` + падение отправителя = `ABORTED` у читателя в середине работы.
Держи `Retries` читателя не меньше, чем у отправителя, и не делай в стримовом читателе
неидемпотентных побочных эффектов «по ходу чтения», которые нельзя повторить.

## 9. Общее состояние и локальный режим

Локально таски — горутины одного процесса: общие глобальные переменные, общий `/tmp`,
общий рабочий каталог. В проде — разные контейнеры, возможно на разных узлах.
Даг, который передаёт данные через глобальную мапу или файл в `/tmp`, локально проходит
и в проде разваливается. Всё межтасковое — только `Output`/`Input` и значения.

## 10. `time.Now()` вместо `rt.LogicalDate()`

Catchup и backfill гоняют исторические раны **сейчас**. Партиция, посчитанная от
`time.Now()`, затрёт сегодняшний день данными за прошлый месяц. Дата данных — только
`rt.LogicalDate()`.

## 11. Неидемпотентный таск

Ретрай, `RetryTask` из админки, повторный запуск остановленного рана и backfill выполняют
таск повторно. `INSERT` без ключа конфликта, «прибавить к счётчику», «отправить письмо»
дадут дубли. Пиши upsert/merge, идемпотентные ключи, снос партиции перед заливкой.

## 12. `BindParams` на ране без параметров

`rt.BindParams(&v)` возвращает ошибку `run has no params`, если ран запущен без них
(а cron-раны обычно без параметров). Если параметры опциональны — сначала
`if len(rt.Params()) > 0`.

## 13. Значения — не канал для данных

`PushValue` — JSON ≤64KB. Список из десятков тысяч id туда не влезет (и не должен):
это артефакт. Параметры рана ограничены тем же 64KB.

`PullValue` у **стримовой** зависимости может не найти значение — отправитель его ещё
не опубликовал. Значения надёжны только через `After`.

Без `LOOM_SERVER_ADDR` (нестандартный раннер) `PushValue`/`PullValue` вернут явную
ошибку. В штатном проде адрес всегда задан, локально значения хранятся файлами.

## 14. Секреты и переменные в локальном режиме не инжектятся

`os.Getenv("PG_DSN")` локально вернёт пусто, если ты не задал переменную окружением
процесса. Это не баг — сообщи об этом в README дага и/или дай понятную ошибку
«PG_DSN is required».

Отсутствующие на control plane имена валят попытку с `launch_failed` ещё до старта
контейнера — таск не выполнится вообще, а в списке дагов админки появится бейдж
«не заполнено».

## 15. Имена

- Даг/таск/артефакт в SDK: `^[a-z0-9][a-z0-9_-]{0,62}$` — **только нижний регистр**,
  без точек и пробелов. Сервер чуть либеральнее, ориентируйся на SDK.
- env-имя: `^[A-Za-z_][A-Za-z0-9_]{0,127}$`, префикс `LOOM_` запрещён (конфликт
  с контрактом), дубли env внутри таска запрещены — секреты и переменные делят
  одно пространство имён.
- **Переименование таска — смена идентичности**: старые раны продолжают жить на снапшоте
  манифеста, новые получают другой граф, история метрик по таску обрывается.
- **Переименование дага — новый шаблон**: старый помечается `orphaned`, его инстансы
  продолжают работать на последнем известном манифесте, но обновляться перестают.

## 16. Даг без тасков

`Validate()` в SDK его пропустит, а регистрация на сервере упадёт с «в даге нет тасков».
Смотри вывод `describe` перед сборкой образа.

## 17. Ошибка объявления не паникует

Ошибки `New`/`Task` копятся и вылезают только из `Validate()` — то есть при `describe`,
`run` и `run --task`. Даг с ошибкой попадает в каталог как `{"name": ..., "error": ...}`
и **не регистрируется**, но остальные даги образа регистрируются нормально. Если
регистрация «прошла, а дага нет» — ищи его `error` в каталоге.

## 18. Порядок объявления тасков

Зависимость передаётся указателем на **уже созданный** таск, поэтому объявляй в
топологическом порядке. Это же гарантирует ацикличность — цикл собрать невозможно.

## 19. `Timeout` без уважения к `ctx`

`Timeout` отменяет `ctx` таска. Если тело таска не смотрит на контекст (голый
`http.Get`, драйвер без ctx, длинный цикл без проверок), попытка провисит до
страховочного kill'а control plane, съедая слот пула. Все блокирующие вызовы — с ctx.

## 20. Ретраи: сколько это по времени

Пауза удваивается с каждой попыткой (база — `RetryDelay` или 30 с), потолок — 30 минут.
`Retries(10)` при базе в минуту — это часы ожидания. Сервер отклонит манифест
с `retries > 100`.

## 21. Ресурсы

- `MemoryLimit` мал → `OOMKilled` (виден в причине падения попытки).
- В docker-executor'е применяются **только limits**, requests игнорируются;
  локально ресурсы игнорируются целиком.
- Значения из кода — рекомендация: оверрайд из админки перекрывает их по-полево
  и подхватывается ретраями без перерегистрации образа.

## 22. Логи

- `rt.Log()` и обычный `fmt.Println`/паника попадают в один лог попытки (fd 1/2
  перехватываются), но `rt.Log()` даёт структуру и атрибуты — предпочитай его.
- Буфер лога — 32k неподтверждённых строк; переполнение **блокирует** таск, а не
  дропает строки. Даг, который льёт по строке на запись из миллиона, будет тормозить
  сам себя — логируй агрегатами.
- Секреты в лог не писать: лог видят все, у кого есть доступ к рану.

## 23. Retention: артефакты не вечны

Раны удаляются по `run_ttl` и `run_keep_last` (настройки инсталляции, могут быть уточнены
на даге). Вместе с раном уходят его артефакты и логи. Артефакт — транспорт между тасками
одного рана, а не хранилище: то, что нужно надолго, даг кладёт в своё постоянное
хранилище сам.

## 24. JSON: только `encoding/json`

Если даг разбирает JSON — стандартной библиотекой. `github.com/goccy/go-json`
**не применять**: его потоковый декодер на длинных ответах рвёт многобайтные символы
на границе внутреннего буфера — молча портит UTF-8 в данных, которые даг раскладывает
дальше. Ловится только на реальных данных в сотни килобайт, а порча строк в чужих
хранилищах дороже любой экономии на разборе.

## 25. HTTP-клиенты: никакого `http.DefaultClient`

Если даг ходит по HTTP, у любого клиента задавай явно: dial-таймаут (~2 с),
TLS-handshake (~2 с), `MaxConnsPerHost`/`MaxIdleConnsPerHost` (~20), при необходимости
`InsecureSkipVerify` для внутренних сервисов с самоподписанными сертификатами.
Общий `Timeout` — по смыслу вызова; для потоковых ответов оставляй нулевым и
ограничивай контекстом (у таска он и так с дедлайном `Timeout`).

Без таймаута установки соединения недоступный бэкенд подвешивает таск до таймаута
попытки — то есть до `Timeout` таска, а не до разумных секунд. Оформляй настройку
одной фабрикой и создавай клиенты только через неё, чтобы она не расползлась
копипастой. Для не-HTTP клиентов (БД, брокеры, gRPC) правило то же: явные таймауты
соединения и лимит пула.

## 26. Dockerfile

Control plane дописывает аргумент (`describe` / `run`) к запуску образа. Значит бинарник
должен быть `ENTRYPOINT`, а `CMD` — пустым:

```dockerfile
FROM gcr.io/distroless/static-debian12
COPY dag /app/dag
ENTRYPOINT ["/app/dag"]
```

`ENTRYPOINT ["/bin/sh","-c","/app/dag"]` или запуск через `CMD` сломают и describe,
и запуск тасков.

## 27. Один образ — несколько дагов

`loom.Main(a, b)` регистрирует два шаблона. Помни: правка кода одного дага пересобирает
образ для **всех** дагов проекта, и синк проекта обновляет их разом. Не сваливай в один
образ пайплайны с разным темпом изменений.

## 28. Новая переменная выкатывается раньше образа

Необъявленную на control plane переменную loom не подставит — попытка падает
в `launch_failed`. Если у проекта включено авто-обновление, образ с новым
`loom.Variable` уронит **ближайший же ран**. Порядок всегда такой: сначала завести
значение на сервере, потом выкатывать образ.

## 29. JSON-типы источника не те, что ты предполагаешь

Go, в отличие от динамических языков, не прощает расхождения типов: там, где питон
делал `int(...)`, Go отвечает `json: cannot unmarshal string into Go value of type int`
и роняет таск на реальных данных.

**Профилируй типы по реальному ответу, а не по коду старой версии или по документации.**
В одном и том же объекте соседние поля вполне могут иметь разные типы: часть чисел
приезжает числами, часть — строками. Классический источник такого — прослойки, которые
сериализуют 64-битные числа строкой (так делает, например, grpc-gateway с `int64`),
но встречается это и просто из-за истории поля.

Что с этим делать:

- поля, которые ты действительно разбираешь, читай через тип с гибким разбором
  (принимающий и число, и строку);
- значения, которые просто перекладываются в приёмник без разбора, держи сырыми
  (`json.RawMessage`) — так они переживут любую смену типа в источнике;
- любое расхождение типов между старой и новой реализацией фиксируй тестом
  (см. `patterns.md`, «Если даг — порт существующей реализации»).

## 30. Пагинация по расчётному числу страниц

Источник живой: пока идёт обход, записи в него добавляются и удаляются, и фиксированное
число страниц, посчитанное из общего количества в первом ответе, **молча теряет хвост
списка**. Для сверок это смертельно — неполный набор ключей означает удаление живых
записей в приёмнике. Обходи **до признака конца** (короткая страница, пустой ответ,
отсутствие курсора), а заявленное количество держи только как предохранитель от
бесконечного цикла — с запасом в несколько страниц.

## 31. Пустой источник — ошибка, а не «нечего делать»

Если даг приводит приёмник в соответствие с источником, пустой ответ источника не повод
вычистить приёмник: гораздо вероятнее, что источник сломался. Явно возвращай ошибку —
ретрай и разбор человеком дешевле, чем восстановление данных.

## 32. «Уже сделано» — не ошибка

Удаление отсутствующей записи, повторная вставка существующей, отмена уже отменённого —
приёмник обычно отвечает на это ошибкой (`404`, `409`, «not found»). Считать её провалом
таска нельзя: ретрай повторит ту же операцию и получит тот же ответ — **таск не выживет
никогда**. Такие исходы считай отдельным счётчиком (`missing=…`, `skipped=…`) и пиши
в лог, чтобы было видно, если они систематические.

Это же обратная сторона идемпотентности (§11): раз таск обязан переживать повтор,
он обязан и признавать уже применённый результат нормой.

## 33. Конкурентная запись в общий приёмник

Если в тот же приёмник пишет не только твой даг (соседние даги, другие сервисы, живой
пользовательский трафик), одновременное изменение одной записи — штатная ситуация, и
приёмник ответит конфликтом версий или блокировкой. Закладывай это в код: повтор
на конфликте, оптимистическая блокировка, `ON CONFLICT`/`retry_on_conflict` — что
предлагает конкретная система. Иначе таск падает не от своей ошибки, а от соседа.

Заодно проверь границы владения: удалять и перезаписывать даг вправе только те поля
и записи, которыми владеет он сам. Остальное пишут другие — и сверка «чего нет
в источнике» не должна их задевать.
