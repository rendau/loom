# loom — проверенные приёмы

Решения, которые окупились на боевых дагах. Это **не требования SDK и не единственный
верный путь**: приёмник может быть любым (БД, поисковый индекс, очередь, файловое
хранилище, чужой API), формат обмена — тоже. Бери то, что подходит задаче, а из
остального — идею, а не букву.

Примеры ниже иллюстрируют приём; конкретные технологии в них случайны.

---

## Раскладка репозитория дагов

Рабочая конвенция для репозитория, где дагов много: один go-модуль, один бинарь, один
образ — на control plane это **один проект**, а даги внутри — его шаблоны. Если даг
один, всё это схлопывается в обычный `main.go`.

```
loom/
  go.mod                      один модуль на все даги (общий кэш сборки в CI)
  Makefile                    build / image / describe / run
  Dockerfile                  копирует готовый бинарь, ENTRYPOINT на него
  cmd/dags/main.go            единственный main: список дагов и loom.Main
  internal/dags/<dag_name>/   даг целиком: граф + тела тасков, точка входа New()
  internal/httpx/             фабрика http-клиентов (единственный способ их создать)
  internal/<format>/          формат обмена между тасками
  internal/loomvar/           общие переменные control plane с описаниями
  internal/<system>/          клиенты внешних систем
```

- Каталог = пакет = имя дага. Стилю go это противоречит (подчёркивания в имени пакета),
  но идентичность «каталог = пакет = имя в логах, в админке и в `--dag`» дороже.
- Пакет дага экспортирует **ровно одну функцию — `New() *loom.DAG`**. Никаких
  `func main()` в пакете дага: единственный main репозитория собирает каталог образа.
- Новый даг подключается двумя строками в `cmd/dags/main.go` — без этого его
  в образе не будет.
- Тела тасков — функции уровня пакета (`fetchFn`, `upsertFn`), а не замыкания
  внутри `New`: их видно по одной и легко читать.
- Расписание в коде не живёт, но полезно держать его комментарием в шапке файла —
  чтобы было с чем сверять то, что выставлено в админке.

```go
func New() *loom.DAG {
	dag := loom.New("catalog_sync", loom.MaxActiveRuns(1))

	fetch := dag.Task("fetch", fetchFn,
		loom.Retries(2), loom.RetryDelay(time.Minute), loom.Timeout(15*time.Minute),
		loomvar.SourceURL(),
	)

	dag.Task("upsert", upsertFn,
		loom.AfterStreamed(fetch),
		loom.Retries(2), loom.RetryDelay(time.Minute), loom.Timeout(30*time.Minute),
		loomvar.SinkURL(),
	)

	return dag
}
```

## Формат обмена между тасками

Артефакт — это просто байтовый поток, формат выбираешь ты. Требование одно:
**он должен быть потоковым**, иначе `AfterStreamed` теряет смысл, а потребитель
вынужден поднять весь набор в память.

Хороший дефолт для наборов однородных записей — **строчный формат** (JSONL: по одному
JSON-документу в строке): читателю не нужен весь массив, чтобы начать работу.
Для однородных числовых/бинарных данных уместнее свой компактный бинарный кадр,
для одного крупного объекта — просто его сериализация.

Что бы ни выбрал:

- писатель — с буфером (`bufio.Writer` поверх `rt.Output`) и **`Flush()` перед
  успешным выходом из таска**;
- читатель — с буфером под ожидаемый размер записи (`bufio.Scanner` с увеличенным
  `Buffer` или `bufio.Reader`);
- если пишешь чужой сырой JSON построчно — прогоняй через `json.Compact`:
  pretty-printed документ с переводами строк сломает строчный формат. Свои структуры
  дешевле писать `json.Encoder.Encode` прямо в буфер потока.

## Стримить, а не материализовать

Главный выигрыш перед «фазами через промежуточное хранилище»: ни один таск не держит
набор данных целиком.

- Весь набор поднимаем, только если алгоритму правда нужен весь набор (например,
  сверка «чего нет в источнике»), и тогда копим **минимум**: ключи, а не записи,
  и в компактном виде — на сотнях тысяч элементов плоский буфер с бинарным поиском
  втрое дешевле `map[string]struct{}`.
- Если полный набор нужен только части потребителей — отправитель пишет **два стрима**:
  тяжёлый с данными и лёгкий с ключами. Тогда сверке не надо разбирать записи,
  а ждёт она листинг, а не выкачку.

```
list ─┬─(stream keys)──▶ fetch ──(stream records)──▶ upsert
      └─(stream keys)──▶ prune
```

Здесь `upsert` пишет в приёмник то, что в источнике есть, а `prune` удаляет то, чего
в нём нет: множества не пересекаются, поэтому оба идут параллельно, а не друг за другом.
Имена тасков — иллюстрация, у твоего дага граф может быть любым.

## Границы тасков

Режь по границам **«своя память, свой ретрай, своя параллельность»**, а не по фазам
существующей реализации. Типичный пример: преобразование записи — функция от одной
записи; отдельным таском оно стоило бы лишнего прогона всех данных через
artifact-сервер, поэтому делается прямо там, где запись уже в руках.

## `AfterStreamed` — режим по умолчанию

- `AfterStreamed` — нормальный режим для «вытащили → разложили».
- `After` — когда таск обязан начать только после успеха отправителя целиком
  и при этом **не читает** его стрим.
- Нужен полный набор, но читаем стрим — всё равно `AfterStreamed`: EOF означает,
  что отправитель успешно завершился, то есть набор полон.

## Параллельность внутри таска

`errgroup` + канал заданий + общий писатель под мьютексом:

```go
g, gCtx := errgroup.WithContext(ctx)
keys := make(chan string, workers)

g.Go(func() error {              // читатель входного стрима
	defer close(keys)
	sc := bufio.NewScanner(in)
	for sc.Scan() {
		select {
		case keys <- sc.Text():
		case <-gCtx.Done():
			return gCtx.Err()
		}
	}
	return sc.Err()               // ошибка чтения = abort стрима упавшим отправителем
})

for range workers {
	g.Go(func() error {
		for k := range keys {
			rec, err := source.Get(gCtx, k)
			if err != nil {
				return fmt.Errorf("get %s: %w", k, err)
			}
			if _, err = w.encode(rec); err != nil { // w — писатель под своим мьютексом
				return err
			}
		}
		return nil
	})
}

if err := g.Wait(); err != nil {
	return err
}
return w.flush()                  // без Flush хвост не попадёт в артефакт
```

- Отдельная горутина-писатель с каналом записей тут обычно ничего не даёт: под замком
  проходит только сериализация, а воркер между двумя записями успевает сходить в сеть.
- **Число воркеров — переменная, а не константа**, если параллельность вообще есть:
  это единственный настоящий рычаг скорости, и подбирать его хочется на живой нагрузке
  без пересборки образа. Обязательно проверяй диапазон — лишний ноль в переменной
  превращает подбор нагрузки в обстрел источника.
- **Пул соединений — с запасом над числом воркеров.** При лимите ровно по соединению
  воркеры ждут не ответа, а свободного слота: закрытое сервером по keep-alive
  освобождается не мгновенно, да и ретрай уходит в новое соединение, пока прежнее
  ещё разбирается. Число одновременных запросов от запаса не растёт — его держат
  сами воркеры.

## Конфигурация

- **По умолчанию `Variable`, а не `Secret`.** Разница только в хранении: значение
  переменной видно в админке, секрета — нет. Адреса сервисов — переменные; секрет
  заводим, когда значение правда нельзя показывать (пароль, токен, ключ).
- **Общие для многих дагов переменные объявляй одним пакетом** — готовые
  `loom.TaskOption` с описанием. Если один и тот же адрес объявляют два десятка дагов,
  описание, скопированное по каталогам, разъедется на первой же правке. Уникальную
  для дага переменную объявляй прямо в нём.
- Держи один формат имён: имя на control plane (`<система>_url`) → то же имя
  в верхнем регистре в контейнере (`SOURCE_URL`).
- **Описание пиши содержательно**: не «адрес сервиса», а формат, пример, умолчание
  и допустимый диапазон. Проверка перед коммитом — `describe`: у каждой переменной
  в манифесте непустое `description`.
- В переменную выносим только то, что хочется менять **на живой нагрузке, не
  пересобирая образ**. Всё остальное (эндпоинты, размеры батчей, имена полей) —
  обычные `const` в файле дага.
- Обязательная переменная — без умолчания: опечатка в имени тихо увела бы прогон
  не туда. Числовая — с проверкой диапазона, нечисловое значение = ошибка (молча
  взять умолчание значит проигнорировать то, что человек задал руками).

## Логи

- Только `rt.Log()` (slog, пары ключ-значение). Никаких `fmt.Println`/`log.Printf`.
- **Итоговая строка таска отвечает на «что сделано» и «куда»**: адрес/имя приёмника
  и все счётчики, **включая нулевые**. Счётчик расхождений полезен только рядом
  с общим объёмом — иначе «расхождений нет» и «обход ничего не увидел» выглядят
  одинаково.
- Таск, работающий минутами, пишет строку прогресса каждые N записей: без неё
  по логам не отличить «идёт медленно» от «встало». Десяток строк на ран — терпимо,
  строка на запись — нет (буфер лога блокирует таск).

## Тесты

- Клиенты внешних систем — тесты на `httptest` (или на локальном экземпляре системы
  в docker).
- Чистые преобразования (нормализация, сборка документа) — обычные табличные тесты;
  это самая ценная часть покрытия, потому что она не требует ни сети, ни loom.
- Граф дага и тела тасков целиком проверяет локальный прогон, а не unit-тест.

### Если даг — порт существующей реализации

Даг считается проверенным не когда он зелёный, а когда его **результат совпал**
с результатом старой версии:

1. вынеси преобразование старой версии в отдельный скрипт и прогони на **реальных**
   данных (сотни записей, не пара придуманных);
2. сравни с выходом Go рекурсивно, **включая типы**: `null` против `0` или `""` —
   расхождение, а не мелочь;
3. совпавший набор положи в `testdata/` как golden-тест — он и фиксирует порт;
4. приёмник для проверки поднимай **локально в docker той же версии**, с боевой
   схемой/маппингом. В боевой приёмник не писать ничего.

## Сборка и выкладка

```dockerfile
FROM alpine:3.22
RUN apk add --no-cache --upgrade ca-certificates tzdata
WORKDIR /app
COPY dag ./dag
ENTRYPOINT ["/app/dag"]     # executor дописывает describe / run
```

```makefile
build:
	CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o build/dag ./cmd/dags
describe:
	go run ./cmd/dags describe
run:
	go run ./cmd/dags run --dag=$(DAG)
```

- Компиляция снаружи, контекст сборки — каталог с готовым бинарём: `docker build`
  стоит секунды.
- Регистрируется **проект** (образ), а не отдельный даг. По подвижному тегу
  (`:latest`) и с `auto_update` — чтобы dagsync сам подхватывал новые сборки;
  регистрация по неподвижному тегу или по `@sha256:` авто-обновление отключает.
- Digest пиннится при регистрации: перезапись тега следующей сборкой ни
  зарегистрированный проект, ни идущий ран не подменяет.
- Один образ = все даги репозитория: **ломающая правка в общем `internal/` уезжает
  всем сразу**. Не сваливай в один образ пайплайны с разным темпом изменений.

## Проверка перед коммитом

```bash
gofmt -l .                                     # пусто
go vet ./... && go test ./...
make describe                                  # каталог образа собирается и валиден
SOURCE_URL=... SINK_URL=... make run DAG=<dag> # локальный прогон целиком
```

Локальный прогон выполняет весь граф в одном процессе, артефакты остаются
в `.loom/runs/<run-id>/` — туда и смотрим, если данные приехали не те.

## Приложение: перенос дага из airflow

Актуально, только если даг переносится с airflow.

| airflow | loom |
|---|---|
| `DAG(dag_id=...)` | `loom.New(name)` |
| `schedule=...`, `catchup=...` | не в коде: задаётся на даге-инстансе в админке |
| `PythonOperator(task_id=...)` | `dag.Task(name, fn, ...)` |
| `a >> b` | `loom.After(a)` / `loom.AfterStreamed(a)` |
| `trigger_rule=ALL_SUCCESS` | дефолт |
| `retries` / `retry_delay` | `loom.Retries(n)` / `loom.RetryDelay(d)` |
| `Variable.get("x")` | `loom.Variable("X_URL", "x_url", "…")` + `os.Getenv` |
| пароль/токен из connection | `loom.Secret("X", "x", "…")` + `os.Getenv` |
| обмен через промежуточное хранилище (S3) | `rt.Output(name)` / `rt.Input(task, name)` |
| XCom | `rt.PushValue` / `rt.PullValue` |
| `logging.info(...)` | `rt.Log().Info(...)` |
| `owner`, `tags` | не переносятся (нет в манифесте) |

Имя дага и семантику данных сохраняй один в один — иначе сверить старую и новую
версию будет нечем. Разбивку на таски, наоборот, не копируй: в airflow фазы резали
под обмен через хранилище, здесь границы другие (см. «Границы тасков»).
